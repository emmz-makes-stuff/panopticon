## 5.1 Cards, pages and history

- **`ChangeCard.PersonalTags`:** `IReadOnlyList<PersonalTagRef(Key, Value)>`, an init property with a `[]` default,
  next to `ProjectTags`. `ChangeCards.Query()` now also includes `Agents → Tags`.
- **`ToCard(change, Guid? viewerMemberId = null)`:** it fills the personal tags from that member's agents only, through
  `PersonalTagsOf(change, memberId)`. That's the union over their agents, one per tag regardless of case, in the casing
  of the agent that reported last, sorted by key then value. With null, there are none.
- **`HistoryEntry`:** it gains positional `ProjectTags` and `PersonalTags` at the end, copied from the viewer's card.
- **Callers:** `ChangeCards.ListAsync`, `ChangePages.GetAsync` and `HistoryAsync` pass `viewer.MemberId`.
- **The tagging endpoint** answers with the caller's own card, `live.For(viewer.MemberId)`.

## 5.2 The live stream

- **`LiveCard(Card, PersonalTags map)`:** a new record in `ChangeCard.cs`. `Card` has no personal tags, and
  `For(memberId)` gives one member's view.
  - `ChangeCards.GetAsync` and `GetIncludingArchivedAsync` now return it.
  - `ToLive` builds the map from the loaded `change_agent_tags`, keyed only by members who have tags.
- **`ChangeEvent.Updated(Card, Scope, PersonalTags)`:** it has `CardFor(memberId)`. `StreamAsync` sends
  `updated.CardFor(viewer.MemberId)`: one dictionary lookup, with no database read.
- **`ChangeBroadcaster.Publish`:** there are two overloads.
  - `Publish(LiveCard, scope)` is what the server uses.
  - `Publish(ChangeCard, scope, map? = null)` is kept for the many existing tests. It throws `ArgumentException` if the
    card already carries personal tags, so a leaky card can't be broadcast by mistake.
- **Design drift (deliberate, small):**
  - D6 says the map is `Tag[]` by member. It's `IReadOnlyList<PersonalTagRef>`, because that's what the card needs.
  - D6 says "the recorder builds it". It's built by `ChangeCards` when the publisher reads the card, from the same
    `change_agent_tags` rows. All three publishers get it this way: `ReportProgressTool`, `ChangeTagEndpoints` and
    `TagChangeTool`.

## 5.3 The Tags filter

- **`TagFilter`:** a closed record hierarchy in `HistoryFilter.cs`, with `ProjectTag(TagId)`, `ProjectKey(ProjectId,
  KeyKey)` and `Personal(KeyKey, ValueKey?)`.
  - `TryParse` handles the `t:`, `k:` and `p:` forms. Keys and values go through `TagText.TryParse`, so `p:key:val:ue`
    keeps the `:` in the value. `k:` must be a bare key.
  - `ToString()` gives the canonical `tag` value.
  - Every malformed value gets one message: `tag must be t:<tag id>, k:<project id>:<key>, or p:<key> or
    p:<key>:<value>.`
- **`HistoryFilter.Tags`:** an init property.
  - `TryParse` gained an `IReadOnlyList<string>? tags` parameter before the `out`s. Blank values are skipped and
    repeats collapsed.
  - More than `TagText.MaxFilterTags` (20) gets the 400 `tag can be given at most 20 times.`
- **`Apply(changes, viewerMemberId)`:** it now takes the viewer's member id, for the personal `EXISTS`. There's one
  `EXISTS` per tag.
- **The endpoints:** the history and metrics endpoints bind `string[]? tag`.
- **`HistoryChoices.Tags`:** a list of `TagChoice(Filter, Project?, Key, Value?)`, where `Filter` is the ready-made
  `tag` value. That's what §8's web should use.
  - **The order:** personal tags first, then each Project by code. Within a group: by key, then the key alone, then a
    bare tag, then values.
  - **A personal bare tag and its key alone** are the same filter (`p:key`), so they're one choice.
  - **Casing:** among casings of one personal tag, the one that sorts last ordinally is shown (lower case where any
    was reported), so reads are deterministic.
