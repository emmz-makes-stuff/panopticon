## What landed

- **`ServerAddress`** (`src/Panopticon.Cli/ServerAddress.cs`) is lifted out of `LoginCommand`, so `login` and `update`
  share it, and `login` behaves as before:
  - `Resolve` takes `--server`, then `PANOPTICON_SERVER_URL`, then the saved login.
  - `TryRoot` normalises the URL to a root with a trailing slash.
  - `ProblemAsync` reads Problem Details `detail`.
- **`UpdateCommand`** (`src/Panopticon.Cli/Update/UpdateCommand.cs`) runs in this order:
  1. Parses `--server`.
  2. Resolves the server. With none, it exits 1, naming `--server` and `panopticon login`.
  3. Gets `/api/cli`. A 404 means "has no CLI builds: <detail>". Any other refusal, an unreachable server, or bad JSON
     each exits 1 with "Nothing was changed."
  4. If the version equals the CLI's, it prints "already up to date" and exits 0.
  5. If there's no entry for `RuntimeInformation.RuntimeIdentifier`, it exits 1, listing the platforms the server
     has.
  6. Streams the download to `<binary dir>/.panopticon-update-<random>`, hashing as it goes, and checks both size and
     SHA-256.
  7. Sets mode 755 on Unix, then hands over to `BinaryReplacer`.

  It prints "Updated panopticon from X to Y." and "Restart your agent…". It sends no token. Every failure deletes the
  temp file.
- **`BinaryReplacer`** (`Update/BinaryReplacer.cs`):
  - On Unix, `File.Move(…, overwrite: true)`.
  - On Windows, binary → `.old`, then new → binary. If the second move fails, the first is undone.
  - The `move` delegate is a test seam.
  - `CleanUpAfterUpdate` deletes `.old` quietly. `CliApp.RunAsync` calls it at every start, but only when the process
    is named `panopticon`, so a test host's `dotnet.old` is never touched.
- **`CliApp`** has `update` in the dispatch and in `--help`.
- **The tests:**
  - **`UpdateCommandTests` (15)** use a stub `HttpMessageHandler` (`disposeHandler: false`, since one test runs twice).
    They cover:
    - a newer build replacing the binary, with mode 755
    - an older build still installed
    - the same version changing nothing, and fetching only the manifest
    - a checksum mismatch, and a short download
    - a server with no builds, no build for this platform, and an unreachable server
    - an unwritable directory (skipped on Windows and as root)
    - no server known
    - the saved login vs the environment, with no `Authorization` header sent
    - the Windows rename and its clean-up, and the Windows undo
    - a usage error
  - **`PublishedCliUpdateTests` (2)** take a copy of the AOT binary and run `update` against Kestrel. One case has a
    9.9.9 catalogue, where the file is replaced (the mtime moves on from 2000-01-01), no temp is left, and the
    replaced binary still runs `--version`. The other has a `0.0.0-dev` catalogue, where nothing changes and the
    mtime stays the same.

## Decisions

- **4.2's "a second run says it's up to date" became a separate same-version test.** The served "build" is a copy of
  the same binary, whose compiled-in version is still `0.0.0-dev`, so a second run against a 9.9.9 server would
  update again. Faking a 9.9.9 binary would mean a second AOT publish (about a minute). Checking the mtime proves the
  replacement, and the separate test covers "already up to date" end to end.
- **The download URL isn't required to share the server's origin.** It's the server's own manifest answer, and
  `PublicUrl` can legitimately differ from the URL someone typed (http vs https, an internal address).
