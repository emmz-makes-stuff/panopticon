## What landed

- **5.1** `Panopticon.Contracts/DeviceLogin.cs`: `DeviceStartRequest/Response`, `DevicePollRequest/Response`,
  `DeviceMember`, and `DevicePollStatus` (string constants: `pending`, `slow_down`, `denied`, `expired`,
  `approved`). They're registered in `ContractsJsonContext` (camelCase, nulls omitted, so a pending poll is just
  `{"status":"pending"}`). The round-trip tests are in `tests/Panopticon.Cli.Tests/ContractsTests.cs`.
- **5.2** `Auth/DeviceEndpoints.cs`, open:
  - `POST /api/device/start {machineName}`: the name is trimmed and must be 1–100 characters, else a 400. It's
    limited to 10 per IP per 15 minutes (a 429). `approveUrl` is built on `SignInEndpoints.LinkRoot` (now
    `internal`): `<PublicUrl>device?code=XXXX-XXXX`.
  - `POST /api/device/poll {deviceSecret}`: a 400 if the secret is missing.
    - Unknown secret, already delivered, or expired: `expired`.
    - Within 5 s of the last poll: `slow_down`, via a conditional `ExecuteUpdate` on `last_polled_at`.
    - Then `denied`, `expired`, `pending`, or `approved` with `{token, member}`.
    - Delivery runs in one transaction: claim `token_delivered_at` conditionally, insert `api_tokens`, set
      `token_id`. Concurrent polls issue one token (tested).
    - If the approver was removed before the poll, the answer is `expired` and no token is issued.
  - Responses go out through `TypedResults.Json(…, ContractsJsonContext…)`, so the server's wire shape matches
    what the CLI deserializes.
- **5.3** These need a session. The POSTs need the D6 header.
  - `GET /api/device/{code}` returns `DeviceLoginView {userCode, machineName, state}`. State is one of `pending`,
    `approved`, `denied` or `expired` (`DeviceLoginStates`), and an unknown or malformed code is a 404.
  - `POST /api/device/{code}/approve|deny` only acts on a pending, unexpired login, atomically, and returns 204.
    Anything else is a 404 "That code isn't valid…".
  - Codes are normalized with `Secrets.NormalizeUserCode`.
  - All three count against `AuthLimits.TryApprovalAttempt` (10/min per session, then 429), since every lookup is
    a guess at a code.
- **5.4** `Auth/TokenEndpoints.cs`:
  - `GET /api/tokens` lists your unrevoked tokens as `TokenView {id, machineName, createdAt, lastUsedAt}`, newest
    first. There's no secret or hash in the response.
  - `DELETE /api/tokens/{id}` returns 204 for your own unrevoked token. Anyone else's, an unknown one or a revoked
    one is a 404.
- Tests: `Auth/DeviceLoginTests.cs` (14), `Auth/DeviceApprovalTests.cs` (6), `Auth/TokenEndpointTests.cs` (4).
  `DeviceLoginTests.StartAsync`/`PollAsync` are `internal static` helpers the other two reuse. 6.3's test token
  helper can build on `TokenEndpointTests.LoginAsync`'s pattern (a real start, approve and poll).

## Decisions (not in design.md)

- **The GET reports state, the decisions are strict.** The page (8.4) should show "isn't valid" for any state
  other than `pending`, and for a 404. That way the spec's single message holds for unknown, expired and used
  codes alike.
- **An unknown device secret polls as `expired`**, not a 404. The CLI then stops cleanly with "run
  `panopticon login` again".
- **An approved but uncollected login still expires at 10 minutes.** The expiry check runs before delivery.
