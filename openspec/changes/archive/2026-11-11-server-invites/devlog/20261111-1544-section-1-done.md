# Section 1 done: inviting to the server

<!-- Section: 1 · Tasks: 1.1–1.3 · Base: 2c569ee -->

Server side of server invites: `POST /api/members`, `ServerInviteEmail` / `ServerInviteJob`,
`AuthLimits.TryServerInvite` (20 an hour per member), `SessionMember.CanInviteMembers`, and the member list showing
every active member to initial members.

**Decisions**

- **Race found and fixed.** Two concurrent invites of one new address both got a 201 (and two emails). The second
  invite waits on the inviter's row lock, but that locking statement's snapshot is older than the first invite's
  commit, so it doesn't see the new member. `FindOrAddAsync`'s later statement does see it, as active, and returned
  it as a success. Fix: `MemberInvites.AddUnlessActiveAsync`, which returns null when its own locking read finds an
  active member. A private `InviteAsync` returns `(Member, WasActive)`, and `FindOrAddAsync` wraps it, so Project
  invites are unchanged. Design D1 is amended to match.
- The inviter's and the invitee's rows are locked in one statement, `ORDER BY id`, the same order as a removal, so
  the two can't deadlock.
- The 403 (not an initial member) comes before the 400 (bad address), so a non-initial member gets 403 whatever
  they send. D1 now lists the steps in this order.
- An email is stored as typed: trimmed, not lowercased, as `MemberEmail.Clean` does elsewhere.
- "Development without Resend" is covered by a unit test of `LoggingEmailSender` sending the invite email, plus
  the existing sender-selection test in `EmailSetupTests`. A Development factory can't sign a client in without the
  capturing sender.

**Self-review:** found a stale doc comment naming `FindOrAddAsync`, and the 400/403 order. Both fixed, and the
member-endpoint header test now covers the new POST (401 without a session, 403 without the request header).
