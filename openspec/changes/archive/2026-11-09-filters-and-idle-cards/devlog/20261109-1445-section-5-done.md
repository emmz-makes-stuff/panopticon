# §5 done: the history's filters

Base `91c97cc`.

## What landed

- **`api.ts`:**
  - `fetchHistory(api, before?, filters = "")` merges a `toQuery` string with `before` through `URLSearchParams`, so a filtered page is `/api/history?repo=…&before=…`.
  - New `fetchHistoryChoices(api)` → `GET /api/history/filters`.
- **`views/history.ts`:**
  - **Keys:** `HISTORY_KEYS`, every dimension but status. A `status` in the address is never sent, and there's no status select.
  - **Filters and the bar:** filters come from `parseFilters(params)`. The `createFilterBar` sits above the list, and a choice navigates to `/history?…`.
  - **Choices:** they load beside the first page. A failure warns in the console (`Couldn't load the history's filter choices.`) and the list still shows; the bar then offers only the chosen values.
  - **`update(params)`:** reparses and runs `restart()`, which makes a new list and loads the first page again. A `generation` ticket drops answers from before a restart, or after the view is left.
  - **Empty states:** a filtered history with no matches shows `.history-empty.no-match` ("No archived changes match these filters.") with a Clear button. Unfiltered, the old empty text stays.
- **`testShell.signedIn()`** answers `/api/history/filters` with empty choices, so the older history tests don't warn.
- **Tests** (`views/history.test.ts`, "history page filters"):
  - a filtered first page;
  - Show more keeping the filters;
  - a filter change restarting in place (same heading element, choices fetched once);
  - the empty filtered state with Clear;
  - the server's choices offered, and a failed choices fetch still listing;
  - status ignored.
