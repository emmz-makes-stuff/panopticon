## What landed

- **`HistoryFilter`** (`src/Panopticon.Server/Changes/HistoryFilter.cs`) has `TryParse(repo, owner, member, machine, client)` and `Apply(IQueryable<Change>)`.
  - **Parsing:** `repo` is `host/owner…/name`, with the middle segments forming the owner. `owner` is `host/owner…`. Values are lower-cased and trimmed, with the same `Key` as `ReportRecorder`.
  - **Bad and blank values:** any empty segment is malformed. A blank value means no filter. On error, the message *starts with* the parameter name (`repo must be …`, `owner must be …`, `member must be a member id.`), and the endpoint returns it as a 400.
  - **Matching:** repo and owner compare the `Repo.*Key` columns exactly, so a subgroup owner is matched whole. Member, machine and client use `c.Agents.Any(…)` on `MemberId`, `MachineNameKey` and `ClientNameKey`.
- **`ChangePages.HistoryAsync(filter, before, limit)`:** the filter goes in before the cursor and paging logic, which is unchanged.
- **`GET /api/history/filters`** (`ChangeEndpoints.HistoryFiltersPath`, member-only) is served by `ChangePages.HistoryChoicesAsync`.
  - **Shape:** `HistoryChoices { repos: CardRepo[], owners: {host, owner}[], members: {id, displayName}[], machines: string[], clients: string[] }`.
  - **Content:** archived changes only, with case-variants merged and the lists sorted case-insensitively. A no-member agent adds no person.
- **Tests:** `tests/Panopticon.Server.Tests/Changes/HistoryFilterTests.cs`. It seeds straight to the database (with a second member, Sam, and the default one renamed Emmz) and covers:
  - a theory over every change-filters scenario, plus case and blank values;
  - 400s naming the parameter;
  - the parse split;
  - filtered paging (60 in the repo and 40 elsewhere, interleaved);
  - a run of equal times under a filter;
  - the choices (an active-only repo and machine are absent);
  - 401s.
