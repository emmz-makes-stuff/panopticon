## 9.1, the model (`filters.ts`)

- **`Filters.tags`:** `Filters.tags?: TagFilter[]` is the one array-valued key. It is never empty: no tags is
  `undefined`.
- **`TagFilter`:** a tagged union, `{kind:"tag",id}`, `{kind:"key",projectId,key}` or
  `{kind:"personal",key,value}`, all lower-cased.
- **Keys and the address:**
  - `FILTER_KEYS` and `HISTORY_KEYS` end with `"tags"`.
  - The query parameter is `TAG_PARAM = "tag"`, repeated once per tag.
  - `SingleFilterKey` excludes `tags`. `filterValue` and the bar's dimensions take it.
- **Parsing (`parseTagFilter`):** it mirrors the server's `TagFilter.TryParse` exactly.
  - The prefix letter is case-sensitive.
  - `k:` needs a GUID and a key with no value.
  - `p:` goes through `parseTag`, so the value is everything after the key's first `:`.
- **What `parseFilters` does with tags:**
  - It ignores blanks and repeats.
  - A malformed value puts `"tags"` in `dropped`.
  - It keeps the first `MAX_FILTER_TAGS = 20` and sets `ParsedFilters.tagsOverLimit` for the rest. This is
    separate from `dropped`, because DESIGN gives the two cases different messages.
  - It sorts canonically: ordinal by `tagFilterValue`, the server's `ToString` form.
- **`toQuery` and `hasFilters`:** `toQuery` writes the tags last, and `hasFilters` counts them only when there are
  some.
- **Matching (`hasTag`):**
  - `t:` matches by id.
  - `k:` needs the change's Project and the key.
  - `p:<key>` matches the bare tag or any value. That is the server's semantics, where the bare tag and the key alone
    are one filter.
  - `p:<key>:<value>` matches only that value.
  - Everything compares without regard to case.
- **`Filterable`:** gains `projectTags` and `personalTags`.

## 9.2, the control (`tagFilter.ts`, `filterBar.ts`)

- **The choices:**
  - `FilterChoices.tags: TagChoice[]` (`filter, project, key, value`) mirrors the server's `TagChoice`.
  - `filterOptions` passes the choices through as `options.tags`. The selects' keys are now an explicit
    `SELECT_KEYS` list.
  - **Dashboard order:** `filterChoices` builds the choices in the server's `ChangePages` order. Personal tags come
    first, then Projects by code without regard to case. Within each group the order is key (ordinal), then rank
    (key alone 0, bare 1, valued 2), then value (ordinal).
  - **Spelling:** a Project tag is spelled as on the newest card. Personal casings merge into one choice, spelled as
    the one sorting last ordinally, as on the server.
- **`createTagFilter(onChange)`:** returns `{ control, chosenLine, update(choices, chosen) }`.
  - **The button:** reads "Any tags", "1 tag" or "N tags", with `filter-select--set`, `aria-expanded` and
    `aria-controls`.
  - **The popover:** a search, then `role="group"` groups ("Yours", then the code).
  - **Key-only entries:** a choice is key-only when its value is null and its group has values for that key. It gets
    "any value", and its values are indented (`--value`). The `TagChoice` alone can't tell a personal bare tag from
    the key alone, so this is derived.
  - **Re-rendering:** the list rebuilds only when the choices change. Otherwise the checkboxes update in place, so
    live updates and toggles keep focus.
  - **The chosen line:** "Showing changes with all of:", then chips with ×, labelled "Remove X from the filter". A
    key alone reads "PAN/language: any", and a tag missing from the choices reads "Unknown tag".
- **`filterBar.update(options, filters, dropped, tagsOverLimit)`:**
  - The new fourth argument comes from `app.ts`, `history.ts` and `metrics.ts`.
  - **The note:** "Dropped a tag filter that wasn't valid." and "Kept the first 20 tags." join the existing "Ignored
    …" line, which no longer lists `tags`.
  - **Order in the bar:** the control comes after Status and before Clear, and the chosen line sits under the bar
    (flex-basis 100%).
- **CSS:** `.filter-tags`, `.tag-filter-*` and `.filter-tags-*`.
  - On history and metrics, `.page button:not(.link-button)` would win, so the button and × rules use selectors
    under `.filter-bar` with enough specificity to beat it.
  - On phones, the control takes a whole row and the popover goes full width.
- **Fixtures:** the history-choices fixtures (`testShell`, and the `history` and `metrics` tests) now carry `tags`.
  `testing.ts` has `TAG_CHOICES`, `TAG_PROJECT` and `BUG_TAG_ID`.

## Gotcha (again)

Tests that click checkboxes must attach `shell.events` to `document.body`, because a detached checkbox fires no
`change`. The history and metrics tag tests do it with `onTestFinished(() => events.remove())`.

## Departures from `web/DESIGN.md`, for the §10.3 human check

- **The picker (§8):** a parse error shows only when the typed text matches no listed tag.
- **The Tags filter:** a click outside closes the popover, but leaves focus where the click put it. Escape still
  returns focus to the button. Moving focus back after a click on another control would steal it.
