## 6.1 `CliConfig`

- **The record:** `SavedLogin` is now `CliConfig(ServerUrl, Token, IReadOnlyList<string>? Tags = null)`, with
  `CliConfig.Empty`, in `Config/CliConfigFile.cs`. The JSON is camelCase (`"tags"`) through `CliJsonContext`, which is
  AOT-safe: the published-binary test round-trips it.
- **`CliConfigFile`:**
  - `Read(stderr)`: lenient, as before. An unreadable file logs "ignoring the saved login…" and counts as none.
  - `ReadStrict()`: throws `InvalidDataException` naming the file only.
  - `Update(change, startOverIfUnreadable)`: the read-modify-write that every command uses. `Write` stays as the
    primitive.
- **My call on an unreadable file:**
  - **`login`** passes `startOverIfUnreadable: true`. That's how it already repaired a broken file.
  - **Tag writes** pass `false`, and refuse, so a broken file is never replaced and its token lost.

## 6.2 `panopticon tags`

- **Where:** `Config/TagsCommand.cs`, wired in `CliApp`. The help lists `tags`, `tags add <tag>...` and
  `tags remove <tag>...`.
- **Listing:** `tags` prints one tag per line, or "No personal tags."
- **Editing:** `add` and `remove` print the resulting list on success.
- **Each edit is all or nothing:** a malformed tag, a duplicate (against saved ones or within the arguments), a 21st
  tag, or removing one that isn't saved exits 1 with "… Nothing was changed.", and the file is byte-identical.
- **Removing a bad entry:** `remove` also accepts a hand-edited malformed entry by its exact text (case-insensitive),
  so a bad file can be repaired from the CLI.
- **Usage:** a bare `add` or `remove`, or an unknown subcommand, prints the usage and exits 1.

## 6.3 The bridge sends personal tags

- **`BridgeSettings.Config`:** an init property. `Resolve` sets it to the file it read. It's null when tests build
  settings directly, and that means no tags, so `[]` is sent.
- **`ProgressReporter.ReadPersonalTags()`:** it runs just before each forward. `ReadStrict`, then
  `TagText.TryParseAll(…, 20)`, then canonical texts.
- **When it fails:** a `BridgeException` naming the file and the tag, never the token. Nothing is sent, so a broken
  file can't silently clear the tags on the server with `[]`. This also applies to archive-watcher reports, which go
  through the same reporter.
- **Design drift:** D8 says the bridge "already reads the login per call". It doesn't: `BridgeSettings` is resolved
  once at start-up. Only the tags are read per report. The login behaviour is unchanged.

## 6.4 The bridge's `tag_change`

- **The tool:** `BridgeTools.TagChangeAsync(change, add?, remove?, project?, repo?)`.
  - `RequireServer` comes first.
  - If `project` or `repo` is missing, it finds the git root. The repo comes from the `origin` remote, through
    `ProgressReporter.ParseRemote`, now `internal static`. The project comes from `ProjectLink.ReadAsync`.
  - With no link file, it fails: "This repo isn't linked to a Project…".
- **Forwarding:** `ServerForwarder.TagChangeAsync` goes through `CallAsync`, so a refusal arrives as "The Panopticon
  server refused the tag change: <server's message>", and for an unknown tag the server lists the Project's tags.
- **Binding:** `BridgeHost`'s tool JSON resolver now combines `ContractsJsonContext` too, so `RepoRef` and
  `IReadOnlyList<string>` bind under AOT.
- **Tool counts:** the tool-list assertions went from 2 to 3 (`tag_change`) in `BridgeTests`, `ListProjectsBridgeTests`,
  `ArchiveWatcherTests` and `PublishedCliTests`.
- **Docs:** `docs/cli.md` has new "Personal tags" and "Tagging a change" sections, the config shape, and troubleshooting
  entries. The tag rules there were checked against `TagText`: key and value are each at most 40 characters, and keys
  use ASCII letters.
