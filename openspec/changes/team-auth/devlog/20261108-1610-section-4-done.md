## What landed

- **4.1** `Auth/MemberEndpoints.cs`, mapped in `ServerSetup.MapPanopticon` after `MapSession`. Every endpoint needs
  `AuthPolicies.Member`. Writes need the D6 header through the existing `RequestHeaderMiddleware`.
  - `GET /api/members` lists active members as `MemberView {id, email, displayName, joinedAt}`, ordered by
    `created_at`. `joinedAt` is `created_at`. **8.3's members page reads these field names.**
  - `POST /api/members {email, displayName?}` returns 201 with the `MemberView`.
    - It's a 400 for an invalid email ("That isn't a valid email address.") or an invalid name, if one is given.
    - It's a 409 for an active member ("<email> is already a member."). A concurrent insert that loses on the
      unique `email_key` is also a 409; only a Postgres unique violation is caught.
    - `InvitedByMemberId` is the inviter.
  - `PATCH /api/members/me {displayName}` returns 200 with the `MemberView`. A blank name or one over 50 characters
    gets a 400.
- **4.2** `DELETE /api/members/{id:guid}` returns 204.
  - It's a 400 for yourself ("You can't remove yourself…") and a 404 for an unknown or already removed member.
  - One transaction (`ExecuteUpdate`/`ExecuteDelete`): it sets `removed_at`, deletes sessions, deletes **unused
    sign-in links**, and revokes tokens (`revoked_at`).
- Tests: `tests/Panopticon.Server.Tests/Auth/MemberEndpointTests.cs`, 20 cases covering every 4.1/4.2 scenario plus
  auth and the header.

## Decisions (not in design.md)

- **Re-inviting a removed member reuses their row.** It keeps the same id, so their agents and reports stay
  theirs. It also keeps their original `created_at` as the join date, and their old display name unless the
  invite gives a new one. `InvitedByMemberId` becomes the new inviter.
- **Removal also deletes their unused sign-in links.** Without that, a link emailed before removal would work again
  if they were re-invited within its 15 minutes, because `ConfirmAsync` only checks that the member is active. A
  test covers it.
- **Test Postgres connections.** With 20 more tests, `make test` hit `53300: sorry, too many clients already`.
  Each test database has its own Npgsql pool, which kept idle connections open for 5 minutes.
  `PostgresFixture` now sets `ConnectionIdleLifetime=2` and `ConnectionPruningInterval=1` on test connection
  strings, and starts the container with `max_connections=300`. This is test-only.
