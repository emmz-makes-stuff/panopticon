# §4 done: `request_visit` and the hook

<!-- Section: 4 · Tasks: 4.1, 4.2, 4.3 ticked · Base: 5a8bb50 -->

**Built:**

- **`Panopticon.Contracts/RequestVisit.cs`** (new):
  - `VisitAnswer(Outcome, Note, AnsweredBy)`, the shape the hook injects;
  - `RequestVisitResult(Reached, Url, Outcome?, Note?, AnsweredBy?)` with `Describe()`, the tool's reply;
  - `RequestVisit.AnswerField` (`panopticon_answer`), `Done`/`Cant`, and `AnswerIn(arguments)`. `AnswerIn` treats a
    malformed answer (not an object, an unknown outcome, no `answeredBy`) as no answer.
  - Both records are in `ContractsJsonContext`, for AOT. `ContractsAssembly.RequestVisitToolName` is `request_visit`.
- **`BridgeTools.RequestVisit`:** `url` and `reason` required, `action` optional. It checks `PromptLimits.VisitProblem`
  and returns a tool error ("This visit can't be requested: …"). It reads the answer from
  `RequestContext<CallToolRequestParams>.Params.Arguments` (an `IDictionary<string, JsonElement>`), not from a bound
  parameter, so `panopticon_answer` stays out of the advertised schema.
- **`HookCommand`:**
  - `IsVisitTool` uses the `[GeneratedRegex]` `^mcp__.*panopticon.*__request_visit$` (the class is now `partial`).
  - `PreToolUse` on the visit tool is `PromptKind.Visit`, and `StateFor` returns null for it, so there's no "working"
    event as well. `PostToolUse` still sets working.
  - `PermissionRequest` for the visit tool is ignored.
  - A visit over the limits isn't posted. It sends working with the tool's activity, not waiting, because the tool
    fails at once.
- **`PromptHookOutput`:** `Visit(input)` reads the URL, reason and action. `For(Visit, …)` writes an `allow` whose
  `updatedInput` is the agent's input minus its own `panopticon_answer`, plus the dashboard's, and adds
  `additionalContext` "Answered by … via Panopticon.".
- **`docs/cli.md`:** four tools in the intro, a "Visit requests" section under away mode, and a line in "Other agents"
  (no hooks means always "ask in the terminal").

**§1's open check is settled.** `RequestVisitBridgeTests` sends `panopticon_answer` through the real MCP client and
bridge host, and the tool gets it. D2 holds with no fallback, and neither Claude Code nor the SDK drops the field.

**Decision: 4.2's integration tests run in process, not against the published binary.** The existing
`PromptHookServerTests` all run `HookCommand` in process against a real server, and `PublishedCliTests`' runner
doesn't feed stdin. AOT safety is covered another way: `GeneratedRegex` is generated at compile time, `make aot`
passes with warnings as errors, and `PublishedCliTests` shows the published binary listing `request_visit`.

**The chained test** (`PromptHookServerTests`, away case) feeds the hook's `updatedInput` straight into the real bridge
tool. It gets back "Done: approved. Answered by … via Panopticon.", which is the whole D1+D2 path in one test.

**Edge for §6 and the release (design D9):** a **new CLI with the old 0.2.0 plugin** isn't fully clean. The old async
`PreToolUse` catch-all matches `request_visit`, so the new hook posts a visit prompt from an async hook. Claude Code
kills that hook after 10s. While away, the card shows a held visit for about 90s, until the wait grace releases it,
though the tool has already told the agent to ask in the terminal. This is harmless but confusing, so ship CLI and
plugin 0.3.0 together, and mention it in the plugin README's upgrade note. D9 should be amended in §6.
