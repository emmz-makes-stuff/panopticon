## What landed

- **`projectTagSection(deps, project)`** (`web/src/views/projects.ts`) is now a module-level export. It returns
  `{ element, redraw }`. I lifted it out of `projectView` so the tests can call `redraw` directly, as 1.1 asks, and so
  that §2's stream can drive the same function. `deps` is `{ api, path, confirm, status, reload }`, and `projectView`
  passes `load` as `reload`.
- **`redraw(project)`:**
  - **Kept as they are:** the `<ul>`, the heading, the empty text, the hint and the add form. They're placed with
    `arrange()`, a helper that moves as few nodes as it can and then puts back focus and an input's selection (moving
    a node blurs it).
  - **The rows** are keyed by lower-cased tag id. A row in rename mode whose id is still there is kept, and `update(tag)`
    gives it the new tag, so Cancel shows the current name. Other rows are rebuilt.
  - **A row being renamed whose tag has gone** sets the status line to "PAN/bug was deleted."
- **The role (`canManage`)** is fixed when the section is built, as design D2 says. A role change isn't live.
- **Own writes** (add, rename, delete) still call `deps.reload()`, which is the page's `load()`, so the whole page
  rebuilds as before.
- **`web/DESIGN.md`:** the Tags section's "Live" bullet now has sub-bullets: only the rows move, a rename in progress
  stays open, the "was deleted." copy, and counts update with the list.

## Decisions

- **Rename label:** an open rename form keeps its "Rename PAN/bug" label even if the tag is renamed elsewhere
  meanwhile. Only Cancel, and the row after it, show the new name. This is cheap and harmless, so I didn't treat it
  as needing a stop.
- **The invite form:** 1.1's "invite-form text left alone" holds by construction, because the invite form isn't in
  the Tags section and `redraw` never touches the page outside it. The direct tests only cover the add form. §2.1's
  shell-level tests should check invite text across a live update.
